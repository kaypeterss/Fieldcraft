# Architecture

## Purpose and scope

Fieldcraft is a browser-based, system-agnostic 2D tabletop for precise competitive wargaming practice. It initially provides manual geometry, positioning, measurement, spatial analysis, and assisted formation movement rather than a rules-heavy videogame. The normal prototype uses a 60 × 44 inch battlefield and supports circle/ellipse/rectangle/convex-polygon footprints, normalized players and units, configurable turns, confirmed pose movement actions, allowance-limited movement sessions, selection, footprint-aware measurement and spatial overlays, data-driven coherency evaluation, and orientation-aware generic-footprint Smart Move ghost previews.

React owns the application chrome and ordinary UI. PixiJS owns the high-frequency tabletop rendering and pointer surface. Pure TypeScript owns authoritative state transitions and geometry. This split keeps core behavior usable in tests and, later, on a multiplayer server or replay worker.

## Coordinates and precision

- Canonical spatial units are tabletop inches, never screen pixels.
- The battlefield origin is its top-left; +X points right and +Y points down.
- Rotation is stored in radians normalized to `[0, 2π)`: zero points along +X and positive rotation appears clockwise in this +Y-down coordinate convention.
- JavaScript number precision is retained in state. Values are rounded only when formatted for display.
- Millimeter/inch conversion is centralized in `src/engine/units.ts` using 25.4 mm per inch.
- Geometry contact uses one centralized `GEOMETRY_EPSILON` (`1e-9` tabletop inches) to absorb floating-point noise. It is not a gameplay gap: exact touching remains legal, and no visible clearance is added.
- The Pixi world container applies the camera translation and pixels-per-inch scale. Pan, zoom, viewport size, and device pixel ratio therefore do not alter gameplay coordinates.
- Pointer intent is the deliberate exception to tabletop-unit geometry: a four-screen-pixel threshold distinguishes a click from a drag consistently at every zoom level. Crossing it may begin movement; sub-threshold jitter never does.

## Domain and state ownership

Authoritative `GameState` is a plain, JSON-serializable object containing the schema version, battlefield, players, models, units, unit definitions, current game context, turn configuration, confirmed action history, deterministic next action sequence, and optional active movement session. A model has stable IDs for itself, its unit, and owner; position; rotation; footprint data; and an optional label. `Footprint` is a plain discriminated union for circle, ellipse, rectangle, and polygon data. The serialized field remains named `base` as a compatibility adapter, so existing schema-version-3 circle state needs no migration; its value is now typed as `Footprint`. Position and rotation form a `Pose` without nesting or changing the serialized model shape.

Units reference canonical models by stable `modelIds`; they never duplicate model objects. A `UnitDefinition` describes what a unit type is and supplies prototype game data such as movement allowance and a data-driven `CoherencyPolicy`. A `Unit` is one match instance with owner, definition reference, and model membership. This makes coherency a Unit→UnitDefinition policy plus Unit→Models query and keeps mutable match state separate from reusable game data. The normal development roster is a realistic movement/Smart Move fixture: 10 × 32mm infantry, 20 × 25mm horde infantry, six 75 × 42mm oval cavalry, five 50mm elite models, three 90 × 52mm heavy ovals, three identical convex vehicle hulls, and 10 × 40mm models with a two-neighbor coherency requirement. The roster is split between both prototype players and starts separated, non-overlapping, battlefield-contained, and coherent. A separate opt-in `?footprints=1` board retains the compact four-shape geometry unit with models initially at 0°, 30°, 45°, and 90°; it exercises translation, individual swept rotation, collision, sliding, coherency, and Smart Move independently from the normal gameplay roster.

Selection, active tool, camera, drag gesture, and measurement workflow are transient UI state. They are deliberately excluded from `GameState`. Pixi display objects, React components, DOM nodes, and callbacks never enter authoritative state.

Transient references to derived views follow the same rule. The measurement workflow stores two generic targets: a tabletop point, stable model ID, or stable unit ID. It never stores a model snapshot or authoritative result. Distance, exact base-edge anchors, and the responsible model pair are recomputed from current models and unit membership, so movement can change both the value and which two unit members are closest without leaving stale derived data in UI state.

Spatial-tool mode, requested range, target-base size, coherency policy source, and the editable custom coherency policy are transient analysis settings. Spatial Coherency's Unit Policy mode resolves the selected unit's actual `UnitDefinition` policy; Custom Analysis remains independent and changing its inputs never changes unit data or Smart Move legality. Distances, in-range membership, closest unit pairs, coherency neighbors, connectedness, and warnings are derived from current authoritative model positions. None are copied into `GameState` or represented by authoritative Pixi objects.

State changes use explicit reducer commands and a pure reducer. These commands are distinct from confirmed domain `GameAction` records: pointer-frequency movement requests are transient inputs, while a successful confirmation appends exactly one immutable `MOVE` record. This lightweight history is not event sourcing and is not itself a game-system policy layer.

Hypothetical formation evaluation is also separate from authoritative state changes. A candidate formation is a serializable map of stable model IDs to independently proposed tabletop positions. Pure candidate validation projects those positions onto a temporary model view and can report battlefield, stationary-collision, internal-candidate-collision, caller-supplied reachability, and optional coherency violations without starting a session, creating an action, or mutating `GameState`.

## Movement sessions and policy

A movement session captures participating model IDs, complete starting poses, a per-model ordered `PoseTrajectory`, derived translation distance, derived accumulated absolute angular rotation, policy-resolved movement used, the serialized movement policy selected when the session began, compact accepted translation paths, and a stable reference point. A trajectory is plain JSON data containing one start pose and ordered segments; every segment records its end pose and explicit signed angular delta. The center is linearly interpolated between adjacent poses, so a segment can retain coupled translation and rotation rather than prematurely collapsing them into unrelated totals. Consecutive collinear translations and same-direction fixed-center rotations may be compacted without losing order or derived metrics. Capturing the policy makes accounting deterministic even if the debug selector changes later. The reference is the geometric centroid of participant centers at session start; its accepted path is translated by the same offsets as the rigid formation and is never recomputed from changing positions. Only accepted tabletop segments and accepted angular sweeps update session metrics; rejected pointer travel does not. Confirm copies each trajectory into the resulting action before clearing the session; Cancel restores captured starting positions and rotations exactly.

The session participant set is fixed at session start. Every subsequent request must contain that complete set, independent of ordering, and every requested endpoint must describe the same shared translation from its model's current position. Partial or internally inconsistent requests are rejected without changing state.

Smart Move preview sessions are separate transient UI state. They capture one model, a partial same-unit selection, or a full unit; selections spanning units are rejected. Selected models are movable while unselected models—including members of the same unit—remain fixed and may satisfy neighbor requirements. A pointer target is an unconstrained tabletop-space intent point and may lie outside the battlefield; candidate model footprints remain battlefield-constrained. A new session starts in LIVE TARGETING. The raw target marker follows frame-throttled pointer input, while solver targets use a small tabletop-distance threshold and bounded cadence; a short settle delay requests the exact final raw target. A canvas click enters LOCKED PREVIEW and bypasses live sampling with an exact target request; later canvas clicks reposition that locked target, while pointer movement and UI interaction cannot change it. Ghosts and preview paths never enter `GameState` and do not receive pointer events.

The same pure `solveSmartMove` implementation remains directly callable by engine tests and executes for the UI in one reusable Web Worker. Worker messages contain only serializable solver snapshots and results; authoritative `GameState`, React, PixiJS, DOM objects, action history, and callbacks stay on the main thread. The main-thread controller permits one in-flight solve and one replaceable latest pending intent, so pointer motion cannot create an unbounded queue. Monotonic request IDs, Smart Move session generations, and a local authoritative-state revision reject obsolete results. A previous ghost may remain visible while newer work is pending, but Apply is disabled until the result matches the current intent. Cancel and tool changes invalidate outstanding work immediately and replace a busy worker so abandoned pathological work cannot delay the next session; an exact lock similarly preempts a different obsolete live solve. Authoritative-state changes invalidate results and enqueue one refreshed current intent. A delayed non-blocking calculation indicator appears only while the current relevant intent remains unresolved, and exact settle and locked requests recover full target precision after sampled live movement.

The Smart Move solver is pure and deterministic. V1 first tests obvious maximum-progress candidates: a full-unit common maximum translation when semantically applicable, then every selected model's individual direct maximum without overshooting the target. A valid fast candidate is accepted before reformation. Only when those candidates fail does the bounded fallback solve movable models in current closest-to-target order, trying furthest useful legal progress first and using fixed or provisionally placed final models as coherency anchors. Intermediate placements need only remain potentially completable; required-neighbor counts and connectedness are authoritative only when the generic evaluator checks the complete projected unit. Small bounded backtracking handles greedy dead ends, and target-centered templates remain a last-resort candidate source rather than the primary strategy. Candidate ranking first maximizes total target progress (`start distance to target - final distance to target`), then uses worst-model and total normalized progress to avoid starvation, with path waste and stable generation order as later tie-breakers. Compactness and spread are not objectives. Generic relationship candidates sample the actual anchor-plus-target configuration-space boundary at the target model's unchanged rotation; pair-boundary intersections provide multi-neighbor candidates. All-circle requests retain the established analytic generation fast path. The generic evaluator enforces the unit's separate required-neighbor count using actual footprint-edge distance.

Reachability is evaluated separately with direct paths or bounded fixed-orientation visibility graphs; pass-over models may cross model blockers but still require exact legal destinations. An all-circle request retains the established analytic circle fast path. Generic requests sample configuration-space exclusion boundaries to generate deterministic waypoint candidates, then validate every accepted segment with exact continuous footprint translation against all blockers. The mover's starting rotation is constant for the complete path. Broad-phase bounds and circumradii may reject irrelevant work or group nearby blockers, but never authorize a path. Path cost consumes movement allowance, while target progress ranks candidate quality, so a detour may cost more than the progress it produces. Fast paths use direct-path checks, while fallback routing can reuse a short-lived visibility graph whose cache identity includes the mover footprint/pose, battlefield, and every blocker footprint/pose. Candidate deduplication uses a sub-visual tabletop tolerance, and routed-candidate exploration remains bounded and furthest-first. Fallback search uses hypothetical sequential occupancy: fixed models stay put, placed models occupy their provisional final positions and free their old positions, and not-yet-placed selected models conservatively remain at their old positions. This front-to-back placement order proves candidate paths but does not mutate authoritative state or create multiple actions. Candidate positions and backtracking, path, and completion work are explicitly bounded. Every model uses its own movement allowance within the current Smart Move operation. Earlier confirmed operations remain in history but do not consume a later operation's allowance, and a unit-level Moved status is informational.

M6.7 retains that fixed-orientation hierarchy as the first result. When its progress is meaningfully short and a stationary footprint or battlefield edge makes orientation relevant, a bounded late fallback tests at most four geometry-derived variants: one shared alignment for up to six selected non-circular models, followed by individual alternatives for up to three models. The candidates align each footprint's longest axis with the target direction, its perpendicular, or a nearby blocker axis. Every proposed turn is checked in sequence at its starting center by the deterministic swept-rotation solver, then the existing fixed-orientation pathfinder runs at the new angles. The accepted ordered trajectories record rotation followed by every translation segment. Movement Envelope checks the full starting-pose envelope through rotation and at each path waypoint; Fixed Rotation Charge and Free Rotation use each trajectory's center-path and angular metrics. Final candidate validation uses proposed rotations as well as positions for collision, battlefield containment, coherency, and connectedness. The existing Worker and stale-result protection also invalidate a preview when its movement-policy request changes. This stage does not search for a later in-route turn or rotate a rigid group as one body; a blocked start-position rotation may safely leave the fixed-orientation result in place. The opt-in `?orientationGap=1` board provides a sealed-gap manual QA fixture.

Every final candidate is checked through the generic candidate-formation validator. It must fit the battlefield, avoid candidate and stationary-model overlap, respect each model's movement allowance for that operation, and satisfy the selected unit definition's coherency policy across the complete projected unit, including fixed members. Selected models are projected simultaneously, so their final coherency relationships are never evaluated against one another's old positions. Inspector, Spatial Unit Policy, and Smart Move all use the same generic evaluator. Local required-neighbor validity and connectedness remain distinct policy concerns; connectedness affects overall validity only when the supplied policy requires it, and all three prototype policies currently do. Range and exclusion overlays are analysis views and are not implicit Smart Move constraints. Ownership remains identity rather than permission. Manual movement remains permissive: it may leave a unit locally invalid or disconnected, which is reported by derived inspector/overlay state rather than blocked.

Movement session lifecycle deliberately separates three operations: Confirm commits the active session and records one `MOVE` action, Cancel discards only the active session and restores its captured start without recording an action, and Undo Last Confirmed Movement restores the immediately preceding pre-confirm authoritative model snapshot while removing its corresponding history record. The current undo slot remains one-level and serializable; a real confirmed change replaces it, a cancelled or no-op session does not, and consuming it clears the slot without creating redo behavior. Undo is available only while its action belongs to the current turn context, so the movement shortcut never rewinds a completed turn.

Applying a valid Smart Move candidate remains a main-thread authoritative operation. Before dispatch, the current result must match the active request, session, and state revision, and the generic candidate validator rechecks current starts, movement allowance, battlefield containment, collisions, and complete-unit coherency. The existing validated-candidate movement command and `createMoveAction` factory then update exactly the meaningfully repositioned selected models atomically and produce one ordinary `MOVE`; the existing undo snapshot restores their exact prior authoritative state. Cancelling, switching tools, solver failure, and preview updates create no action and do not disturb undo history.

During an individual-model session, a genuine click on another model in the same unit dispatches that same Confirm command and then hands selection to the clicked model. The existing click-versus-drag threshold prevents pointer-down or drag intent from confirming. A no-op confirmation clears the session without creating history; different-unit clicks and every multi-model session remain blocked until explicitly confirmed or cancelled. Selection handoff never starts movement or a path for the new model.

## Game structure and confirmed actions

`Player` is a lightweight match entity with a stable ID and display name. Unit and model ownership continues to use stable owner IDs, which resolve to these players. Accounts, authentication, and permissions remain outside the domain.

`GameContext` separates player-facing and internal turn concepts. `round` and `turn` form the human-readable context, with `turn` derived from the active player's index in the configured order and resetting each round. `turnSequence` is monotonic across rounds, while `turnId` provides stable identity from that sequence. `TurnConfiguration` supplies the prototype player order and may later supply a phase list. The current two-player Player 1 → Player 2 → next-round cycle is data in the initial configuration, not a rule embedded in movement or geometry. Ending a turn is rejected while movement is active; otherwise it advances through that configuration. The prototype has no enabled phases.

Confirmed `GameAction` records use a deterministic sequence and action ID and snapshot their round, display turn, internal turn sequence, stable turn ID, actor, optional phase, and action-specific payload. Action sequence numbers are monotonic and are never reused after Undo. The first action type, `MOVE`, stores affected model, unit, and owner IDs together with copied starting/final poses, ordered pose trajectories, and per-model movement used; position-only projections remain as temporary compatibility fields for existing history consumers. A small pure action factory builds this canonical record from any already-validated move, so manual confirmation and solver results share the same serialized action shape. Historical payloads therefore cannot be mutated by later tabletop movement. Query helpers derive current-turn movement status and filter history by player, unit, round, turn, type, or recency without React or PixiJS dependencies.

Movement status is informational. The generic engine deliberately allows another move after a unit is marked Moved; a future game-system policy may ask the action queries whether a move is allowed, but Milestone 4 supplies no such restriction. Turn changes alter the query context without deleting history. The one-level movement undo removes its matching `MOVE` action only within the same live turn; arbitrary history editing, redo, and replay remain future systems.

Movement allowance is resolved from Model→Unit→UnitDefinition. M6.4 exposes three generic serialized prototype policies: Movement Envelope, one Fixed Rotation Charge per session, and Free Rotation. Movement Envelope is a reach/pose rule, not path-cost accounting: for starting footprint `S` and allowance `R`, a candidate footprint `C` is legal exactly when `C ⊆ S ⊕ disk(R)`. For convex footprints this is evaluated with exact shape support functions as `max_u(h_C(u) - h_S(u), 0) ≤ R`. A fixed-orientation translation therefore retains the complete center allowance, while changing orientation uses the actual circle, ellipse, rectangle, or convex-polygon silhouette. If rotation would expand the footprint outside the envelope, the center is projected to the closest legal point, producing the minimum automatic retreat for that orientation. Rotating first correspondingly reduces later center reach. Circle self-rotation has no geometric effect.

Fixed Rotation Charge and Free Rotation remain distinct scalar trajectory-cost policies. The fixed policy charges once when the first meaningful rotation is accepted, so dividing or reversing a gesture cannot evade or multiply the charge; Free Rotation charges center-path translation only. This distinction is intentional: path/travel cost and envelope/reach are different abstractions and game-system adapters may choose either. Under Movement Envelope, `movementUsed` records current geometric reach; under path-cost policies it records accumulated cost. History queries may total records for display or future policy, but the generic engine does not subtract that total from a later operation. Movement-use/action limits per turn are a separate future game-system policy. No maximum use count is currently enforced, and the number of `MoveAction` records must not be assumed to equal the number of unit movement activations.

Input submits requested tabletop destinations for the complete active session, which are verified to represent one shared translation. The pure movement API accepts participating model IDs and that translation explicitly; it does not pretend to validate independently proposed endpoints. One bounded rigid-translation solver handles both individual and multi-model movement. It finds the earliest continuous contacts across every moving-model/non-moving-model pair, advances every participant by one shared offset, and projects the untravelled requested vector into the directions allowed by all active contact normals. Contacts whose travel fractions differ by no more than the centralized tabletop tolerance are handled as one deterministic, ID-sorted constraint set. If no shared legal component remains, movement stops.

Selected models never slide independently. Every accepted straight or tangent segment is applied identically to the entire selected formation, preserving exact relative positions. Under a scalar path-cost policy its length is charged to every participant; under Movement Envelope each participant's actual footprint pose is constrained by its own start pose and allowance. The first participant to reach any active policy constraint limits the group. Per-model pass-over capability suppresses that model's path contact while destination overlap remains illegal. Additional constraint sources such as terrain can later join this resolver without moving policy into PixiJS.

Battlefield edges participate in the same movement-constraint philosophy as model contacts. A footprint's fixed-orientation bounds define its legal center interval; the center alone never defines edge validity. At first contact, each active edge contributes an inward normal, so outward movement is removed while tangential or away movement remains available. Rejected outward travel contributes no movement distance. A rigid group uses one shared edge constraint from whichever selected footprint reaches an edge first, preserving formation.

Manual rotation is deliberately an individual-model operation. A selected model exposes a Pixi rotation handle; pointer angle around the model center requests an absolute preview orientation while the reducer resolves the shortest signed angular delta from the current accepted pose. Rotation and translation may be combined within one movement session. Multi-model rigid rotation is deferred, so mixed groups continue to translate without changing relative rotations.

## Geometry and rendering

Geometry in `src/engine/geometry` has no React, PixiJS, or browser dependency. It owns distances and battlefield constraints; it does not interpret game rules. The pure footprint facade accepts serialized `Footprint` plus `Pose` values and exposes exact static bounds, point/rectangle intersection, closest points, strict overlap, and battlefield containment for circles, ellipses, oriented rectangles, and convex polygons. Circle/circle operations retain the proven circle geometry for parity; cross-shape queries use a small deterministic support-mapping/GJK kernel rather than bounding approximations or a physics engine. Serialized polygons are finite, non-degenerate, uniquely vertexed, non-self-intersecting, and canonically clockwise in tabletop coordinates. M6.1 deliberately accepts convex polygons only; concave inputs fail validation with an explicit error and may later be decomposed by an import adapter. Pixi objects, transformed vertices, geometry methods, caches, and collision structures never enter authoritative state.

Pixi renders each footprint's actual silhouette at its pose and uses the same footprint facade for point and selection-box hits. Measurement, range membership, minimum unit distance, coherency, hypothetical final-placement validation, manual movement, pathfinding, and Smart Move therefore use actual geometry. Range outlines are sampled from the support mapping of the source footprint plus a circular offset. Exclusion outlines use the source footprint plus the reflected target footprint at its explicit fixed orientation plus the requested separation; exact membership remains a closest-footprint query. Sampling affects visualization only and never authoritative spatial results; pathfinding uses sampled exclusion boundaries only to propose graph nodes and exact footprint sweeps to accept edges. Manual translation and individual rotation support every footprint. Smart Move supports mixed circle, ellipse, rectangle, and convex-polygon units; its orientation fallback may rotate a non-circular model before a fixed-orientation route. Ghosts draw each actual footprint at its proposed final pose. No non-circular shape is silently replaced with a bounding circle. Group manual movement calculates one allowed translation for mixed selections, preserving relative positions and rotations while keeping every footprint inside the battlefield.

Placement validity is also generic geometry: footprints may touch but may not overlap. Rigid movement resolves battlefield contacts continuously and rejects any final placement that overlaps a non-moving model; participating models need no internal recheck because their captured relative formation cannot change. Independently positioned candidate formations use a separate pure validator that checks every candidate base against the battlefield, stationary models, and every other candidate. PixiJS only proposes tabletop movement; it is never the authority for collision validity.

Movement distinguishes **path validity** from **destination validity**. Circle/circle sweeps retain the proven analytic center-segment test. Every mixed or non-circular pair uses bounded conservative advancement over exact closest-footprint distance, preserving each footprint's current rotation and returning its earliest safe contact rather than a bounding approximation. Normal models therefore resolve to first contact instead of tunneling. `canPassOverModels` is a generic capability on the model, not an Age of Sigmar rule: capable models skip path blocking but still must finish in a non-overlapping destination.

Swept rotation uses a separate bounded deterministic conservative-advancement solver. At each accepted angle it measures exact footprint-to-footprint clearance and clearance to all battlefield edges. Dividing that clearance by the rotating footprint's circumradius gives a conservative safe angular step because no footprint point can travel farther per radian. Near contact, a small deterministically subdivided probe distinguishes rotation into contact from rotation back away; the first illegal substep is bisected to the maximum legal angle. Under Movement Envelope, the accepted rotated footprint is then projected to the closest legal center and that retreat is resolved through the ordinary translation collision/boundary layer; the resulting trajectory segment retains both the angular change and center retreat. Circles retain their stored angle but bypass the sweep because their silhouette is rotation-invariant.

Contact handling is directional and independent of footprint type. Circle pairs use their radial normal; generic sweeps use the separating normal derived from closest points on the two footprints immediately before contact. If a model starts touching, or is within the geometry epsilon of a tiny accidental overlap, only meaningful inward movement is blocked while movement away, tangent, or only numerically inward remains available. This prevents repeated near-zero contact from consuming the iteration budget and trapping the dragged footprint.

Multiple active constraints may combine model contacts and battlefield boundaries. Near-simultaneous contacts are collected within the same centralized tolerance and projected together; corners therefore stop cleanly when no shared legal vector remains, while movement away from either active edge resumes immediately. This is constraint projection, not automatic pathfinding or routing.

Individual collision response uses the contact normal only to project out inward travel; it adds no impulse or automatic detour. A direct center-line push therefore remains stopped, a diagonal push can continue along the local tangent, and a second blocker or battlefield edge can stop that tangent attempt. Final placement validation remains authoritative, so the bounded response cannot squeeze through an illegal gap.

Pose trajectory, envelope geometry, swept geometry, and game-system path cost are separate concerns. The trajectory layer derives center-path length, total absolute angular travel, and whether rotation occurred. Movement Envelope reads starting and candidate poses directly instead of reducing ordered movement to additive scalars. The pure path-cost layer handles Fixed Rotation Charge and Free Rotation. Exact maximum physical footprint-point path length and maximum footprint-point displacement remain deliberately deferred, but ordered pose segments retain the coupling information those future calculations require. Fixed-orientation M6.5 paths can be represented directly as trajectories whose segments have zero angular delta. These prototype policies are generic configuration, not authoritative rules for a specific game system.

The Pixi adapter reads domain state, projects inches through the camera, draws models, and translates pointer gestures into actions or UI callbacks. Camera pan input is tool-independent: non-primary pointer-down is resolved before board, model, or rotation-handle actions, so panning cannot select, measure, move, rotate, or change a Smart Move target. In selection mode, a regular click resolves to one model, Shift toggles model membership, and Ctrl/Cmd selects the clicked model's whole unit. Ctrl/Cmd has precedence if Shift is also held; no fourth combination mode exists. A single selected model shows a gold rotation handle and live angle label. Unit selection is a click-only gesture and never arms movement. In measurement mode, a model click creates a model target, Ctrl/Cmd-click creates its unit target, and a click on empty battlefield creates a point target. Completing one pair leaves one active measurement; the next target starts a replacement measurement.

One non-interactive movement overlay renders the session reference path for either an individual or rigid group. It shows accepted movement—not the raw pointer request—and is derived only from serializable tabletop coordinates. Measurement target feedback and its exact anchor-to-anchor line are also non-interactive and render above model tokens and other analysis graphics. Rendering order is presentation-only and is not part of gameplay logic. Future terrain must similarly separate visual artwork from collision/gameplay geometry.

Enter dispatches the same confirm action as the existing button. Escape first cancels an active movement session; when no movement is active it clears an in-progress or completed measurement, then selection. Ctrl/Cmd+Z dispatches the movement undo action only outside editable controls; text inputs, textareas, selects, and contenteditable surfaces retain normal browser editing behavior. Keyboard repeat is safe because the reducer requires an active session for confirmation and consumes the one-level undo slot exactly once.

## Spatial queries and coherency

`src/engine/spatial.ts` is the game-agnostic spatial-query boundary. It operates only in tabletop inches on domain models and points, and delegates footprint queries to the generic geometry facade. The measurement tool uses this same high-level geometry, preventing divergent distance definitions. Current queries cover model-to-model and model-to-point distance with closest anchors, model/unit range membership, unit-to-unit and unit-to-point minimum distance with the responsible model or model pair, footprint-offset range outlines, and target-origin exclusion membership/outlines for an explicit footprint and fixed orientation. The legacy radius helpers remain circular-only compatibility APIs.

`src/tools/measurement.ts` resolves all ordered combinations of point, model, and unit targets against live state. Point-to-point uses Euclidean distance. Every model measures from its actual rotated footprint edge, and a unit measures from whichever current member yields the minimum footprint-edge distance. Results preserve target order, return `startAnchor` and `endAnchor` in tabletop coordinates, and identify responsible models where applicable. Touching, overlapping, point-inside-footprint, and coincident-origin cases return zero with deterministic coincident anchors; missing models and empty or unresolvable units return no result. Ownership and turn state do not alter these spatial facts.

Range comparisons include the centralized geometry epsilon, so an exact boundary counts while meaningfully outside geometry does not. Model-range queries exclude their source by default and make inclusion explicit. Unit range is evaluated as an `any` query across source models; minimum unit distance is a straightforward pairwise minimum. These APIs describe spatial facts only and assign no shooting, engagement, deployment, or other game meaning.

`src/engine/coherency.ts` applies a small data-driven `{ distance, requiredNeighbors, requireConnected? }` policy to a unit. It builds one adjacency graph from base-edge distances and returns per-model neighbor results, links, local-neighbor validity, connectedness, connected components, and policy-aware overall coherency. Local validity and graph connectedness remain separate outputs; connectedness affects overall validity only when requested. All three prototype definitions request it, and Inspector, Spatial Unit Policy, and Smart Move validate against this same evaluator. Spatial Custom Analysis supplies an independent editable policy. A future GameSystem→rules/configuration→policy adapter can replace prototype definitions without changing the solver.

Spatial is an independent transient analysis overlay, not a primary pointer tool. Select remains the primary interaction while Spatial is opened, so the existing selection, individual/rigid translation, rotation, Confirm, Cancel, Undo, and camera paths are reused without a Spatial-specific movement implementation. Range areas are the actual source footprint dilated by the requested range. Exclusion areas are target-origin configuration-space obstacles built from the actual source and target footprints, the target's selected current orientation, and required separation. The UI may instead choose an arbitrary circular target preset. Unit overlays draw each derived convex outline without generating persistent polygon unions. Coherency links use the exact closest edge anchors, while footprint-shaped validity indicators and explicit warning markers agree with the same evaluator used by Inspector. All overlay graphics are derived and redrawn from current authoritative poses, have pointer interaction disabled, and never affect collision or movement legality. A single selected model may identify its containing unit for coherency analysis, allowing one member to move or rotate while the whole unit's derived result remains visible.

## Extension boundaries

- **Game systems:** Generic state must not hardcode Age of Sigmar terms or statistics. A later game-system module can supply definitions, terminology, data version, coherency policies, and optional rule validators.
- **Army import:** External formats belong in adapters that produce a normalized internal army list. List composition, game-data definitions, and the resolved playable army remain separate concepts.
- **Game-data versions:** Saved games and replays must retain a version reference or immutable snapshot so later balance changes cannot rewrite history.
- **Multiplayer:** The eventual server is authoritative. Clients submit actions; the server validates pure state transitions and broadcasts resulting state. Stable IDs and JSON-safe state are prerequisites already enforced here.
- **Replay:** Deterministic actions and state snapshots can later support undo, replay, inspection, and branching. Random results must eventually be explicit or generated through controlled RNG.
- **Smart Move extensions:** V1 has one free-position intent and fixed orientation throughout each path. Future orientation choice, terrain, exclusion policy, special movement, and tactical intent modes should extend explicit generation, validation, path, or scoring inputs rather than read UI overlay visibility or introduce game-name checks.

## Performance principles

Smart Move keeps the ordinary model-selection semantics while active: a model click selects, Shift toggles membership, Ctrl/Cmd selects its unit, and an empty-table click locks the target. A selection change invalidates any old preview and begins a fresh same-unit Smart Move session. In the Worker, live, settle, and live state-refresh searches have a 1,000 ms wall-clock budget; a locked exact target has 10,000 ms. The pure solver cooperatively checks a deadline between bounded search branches, while a main-thread watchdog terminates and replaces a Worker that does not respond by its deadline. A fully validated candidate found before the limit may be returned; otherwise the UI reports a search limit and keeps Apply disabled. The watchdog also releases a pending newer intent if an obsolete solve stalls. Calculation status is neutral until a current result exists.

PixiJS handles pointer-frequency visual work and large tabletop scenes; React is limited to normal UI and authoritative state coordination. Optimize from profiling rather than adding premature spatial indexes or generalized rule frameworks. The current renderer redraws this small prototype scene after state changes; model-level reconciliation or spatial indexing can be introduced when measured scale requires it.

## Deliberate omissions

No Army, GameSystem, importer, terrain, objectives, deployment, engagement enforcement, networking, replay, terrain navigation, or authoritative game-specific movement policy is included. Fixed-orientation footprint pathfinding is deliberately bounded and may miss routes that require more sampled candidates or a change of orientation. Smart Move supports every current convex footprint but may still miss difficult coordinated solutions because candidate, detour, and backtracking exploration are bounded. Manual movement supports individual translation and swept rotation; rigid-group rotation, orientation-changing pathfinding, and Smart Move orientation choice remain later M6 milestones.
